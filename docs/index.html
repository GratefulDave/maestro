Code moves.

Maestro executes software plans as dependency graphs. Every attempt gets an isolated worktree, every agent gets a visible Herdr pane, and every accepted change crosses deterministic gates before merge. Workspace coordination composes independent repository runs without weakening their local authority.

01 / 08

Small control plane. Hard boundaries.

Prompts propose work; Python owns execution. Plans, scheduling, acceptance, recovery, and publication remain explicit, typed, and inspectable.

Plan

Validated before execution

Typed agent and code nodes declare dependencies, outputs, gates, evidence, and model configuration.

Isolation

One attempt, one worktree

Concurrent ready nodes cannot share mutable files or silently certify another node’s output.

Acceptance

Evidence before merge

Scoped gates, verification verdicts, integration gates, and ancestry checks determine publication.

Trace

SQLite is durable truth

Transitions, attempts, receipts, outcomes, and operator escapes survive restart without log reconstruction.

02 / 08

Execution model

Only dependency-ready nodes enter the worker pool. Completion order may vary; merge order does not.

01ProjectPersist the validated DAG and immutable plan digest.
02ProvisionCreate worktree, run ecosystem setup, capture baseline.
03ExecuteLaunch omp or Claude in a correlated visible pane.
04VerifyRun scoped gate and classify structured evidence.
05MergeConsume output SHA in deterministic frontier order.
Concurrency invariant. Independent ready nodes execute together. Shared output ownership, missing dependencies, and gate-core aliasing are refused before launch.

04 / 08

Node lifecycle

Six terminal and non-terminal states make partial work explicit. Every legal transition is transactional.

PENDING→ RUNNING→ VERIFIED→ MERGED or BLOCKED CANCELLED
Retry

Same-session, bounded

Semantic, environmental, and launcher-transient failures follow distinct budgets. Credential failures refuse retry; only semantic retries receive a mutated prompt.

Recovery

Restart-safe

Persisted state reconstructs quiescent work. Inherited running attempts become environmental failures and relaunch; unreachable panes are recorded as orphans, never adopted across processes.

05 / 08

Visible Herdr launcher

Every agent node runs in a visible pane. Route selects the CLI; model selects the intelligence behind it. Those axes never collapse. Only omp and Claude routes with valid signed route receipts are admitted.

OperationContract
launch(spec)Allocate pane, bind exact worktree cwd, start explicit omp or Claude route, return correlation handle.
poll(handle)Report starting, running, exited, or gone. Herdr state is advisory; the last complete structured transcript envelope synthesizes terminal exit truth.
cancel(handle)Close the pane and terminate a harness-owned process group by bounded TERM→KILL ladder; report quiescence or pane failures.
reclaim(token)Recover exact correlation matches only; never infer ownership from nearby panes.
classify(error)Map launch faults into fixed configuration, authentication, transient, protocol, or execution classes.
provision(worktree)Run ecosystem setup after worktree creation and before baseline or pre-gate measurement.
wait_for_interactive_agent(name)Block on herdr agent wait <name> --until idle --timeout, the documented readiness gate for coding agents. No undocumented status field is polled and no per-agent startup banner is scraped from the pane.
submit_agent_prompt(target, text)Deliver one turn with herdr agent prompt <target> <text> --wait --until <status> --timeout, which submits the text and its Enter atomically and proves the composer accepted them. On agent_prompt_stalled the recovery is a single agent send-keys <target> enter followed by agent wait, never a second prompt.
Command boundary. Coding agents are driven only through the agent commands. The pane commands address ordinary terminals, servers, and shells, so pane run against a pane hosting a coding agent types the prompt as a shell command instead of handing it to the composer. A prompt submitted without --wait reports success even when the text is left sitting unsubmitted, which is indistinguishable from a delivered turn until the turn times out.
06 / 08

Workspace coordinator

Multi-repository work composes complete single-repository runs. WorkspaceCoordinator owns repository ordering and execution; CoordinatorStore owns durable state; WorkspacePublisher owns publication. Each participant keeps its own plan, scheduler, verification, and final-acceptance authority.

01FinalizeCanonical workspace bytes receive a SHA-256 digest and an Ed25519 receipt bound to each writable child PASS receipt.
02CoordinateLease the acyclic repository DAG and start independent ready participants concurrently.
03ComposePin accepted candidate SHAs in detached read-only acceptance worktrees, then run ordered global gates.
04PublishPersist a compare-and-swap target vector before local-ref or pull-request publication.
Authorization

Closed, signed workspace

maestro-workspace.v1 declares ordered write/read-only repositories, exact base commits, child-plan bindings, dependencies, gates, and publication mode. Stored canonical bytes—not a reserialization—are digest authority.

Participants

Strict process boundary

A writable repository returns fresh, bounded maestro-participant-result.v1 output. Its accepted SHA must equal the candidate head and descend from the declared base; zero exit alone is failure.

Recovery

Exact identities survive restart

Durable state binds repository paths, child run IDs, candidate refs, worktrees, accepted SHAs, gates, and lease ownership. Accepted repositories and recorded gates never relaunch.

Publication

Partial success is not acceptance

none, local_refs, and pull_requests are explicit modes. Local refs use compare-and-swap rollback; PR publishing uses force-with-lease and may require manual recovery.

07 / 08

Operator CLI

The public surface exposes validation, publication, execution, inspection, recovery, and deliberate escapes.

# route admission
$ ./maestro.py bootstrap

# authoring
$ ./maestro.py plan validate plan.json
$ ./maestro.py plan finalize plan.json
$ ./maestro.py plan show <digest>
$ ./maestro.py plan list

# execution and inspection
$ ./maestro.py run start <digest>
$ ./maestro.py run status <run-id>
$ ./maestro.py run cancel <run-id>
$ ./maestro.py run resume <run-id>

# explicit operator escapes
$ ./maestro.py retry <run-id> <node-id>
$ ./maestro.py skip <run-id> <node-id> --accept-sha <sha>
$ ./maestro.py abandon <run-id> <node-id>

# workspace coordination
$ ./maestro.py workspace validate --manifest-file <workspace.json>
$ ./maestro.py workspace finalize --manifest-file <workspace.json> --plan-receipt-dir <dir> --workspace-receipt-dir <dir> --data-dir <dir> --verify-key <hex> --signing-seed <hex>
$ ./maestro.py workspace start --manifest-file <workspace.json> --workspace-receipt-dir <dir> --data-dir <dir> --verify-key <hex> --db <db> --state-root <dir> --run-id <id> --max-workers <n> --lease-owner <id> --lease-stale-after-s <seconds> --participant-timeout-s <seconds> --cancellation-timeout-s <seconds> --poll-interval-s <seconds>
$ ./maestro.py workspace status --db <db> --run-id <id>
$ ./maestro.py workspace cancel --db <db> --run-id <id> --actor <actor>
$ ./maestro.py workspace resume --manifest-file <workspace.json> --workspace-receipt-dir <dir> --data-dir <dir> --verify-key <hex> --db <db> --state-root <dir> --run-id <id> --max-workers <n> --lease-owner <id> --lease-stale-after-s <seconds> --participant-timeout-s <seconds> --cancellation-timeout-s <seconds> --poll-interval-s <seconds>
$ ./maestro.py workspace publish --manifest-dir <dir> --db <db> --run-id <id> --actor <actor>
$ ./maestro.py workspace rollback --manifest-dir <dir> --db <db> --run-id <id> --actor <actor>
Bootstrap. bootstrap provisions key material and admits every configured route before any run may use it. Admission is a real capture, not a version probe: each route answers a marker prompt in a visible pane, answers it again from a resumed session to prove continuity, and is then cancelled to prove the pane closes. Only then is a signed route receipt written. A route whose receipt already verifies is reported as reused.
