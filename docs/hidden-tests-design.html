Hidden tests

Written after the lane-routing-chemical investigation established that current test visibility is deliberate, not a defect. This page proposes replacing that design. Markdown source: hidden-tests-design.md.

0. What is being changedvault + schema built

Today a tests node merges into the integration branch, every downstream build lane inherits its files, and the build lane’s own commit must carry them byte-identically (tests_chain.compare_test_bytes, PairingRefusal.BYTES_SUBSTITUTED). The implementation builder can read the tests it is judged by. That is the specification working as written, not a leak.

This design withholds the test files from the build phase and executes them out of band.

The entire value of the feature depends on a property this design cannot supply on its own: the builder must be unable to read the hidden tests. A linked git worktree shares its parent repository’s object database, so a hidden-tests commit stored as a ref in the run repository is readable from the builder’s worktree with one git cat-file.

What exists now: hidden-test attempts live in a separate bare repo under harness-private state (adw_modules/hidden_vault.py), proven by tests/test_hidden_test_containment.py (cat-file --batch-all-objects). That is the vault. The composed evaluation tree that would fetch those blobs into a gate scratch is not built, so a v5 plan cannot start a run. Absolute-path read of harness state is still possible.

1. Core mechanism: the composed evaluation treeintended

Not built. Intended: hidden test bytes never enter the integration branch during the build phase and never enter any builder worktree. Every gate run for a hidden-paired build node would execute in a harness-private scratch tree composed at execution time from two immutable commits — the tree under test, and the hidden test paths from the accepted tests candidate sha.

GIT_INDEX_FILE=<private>  git read-tree <tree-under-test>
GIT_INDEX_FILE=<private>  git update-index --add --cacheinfo <mode>,<blob>,<hidden path>
GIT_INDEX_FILE=<private>  git write-tree            ->  composed_tree_sha

composed_tree_sha would be the audit anchor: a deterministic function of (tree_under_test_sha, accepted_tests_sha, sorted(hidden_paths)). Adjudicators would recompute it rather than trusting a runner report.

1.1 Why composition rather than “run the tests from somewhere else”

Pointing the runner at test files on another path fails on imports. Composition would put both in one tree so existing runner-resolution assumptions hold. None of this executes today.

2. Requirement 1 — falsifiability without the test in the worktreeintended

Not built. §7.4 requires the node’s gate to be red before the node’s work and green after, and red for the intended reason. The intended composed bracket:

ClauseTree composed fromRequired verdict
pre-node (chain root)chain-root integration head + accepted testsRED
post-nodecandidate output_sha + accepted testsGREEN, passed >= min_cases
output falsificationcandidate with measured-delta paths reverted to chain-root base, + accepted testsRED

Intended new refusal: HIDDEN_GATE_RED_BY_IMPORT — a pre-gate red because the tree fails to import or collect is not a valid red. A hidden test suite would have to import lazily enough to fail by assertion at the pre-gate. This authoring burden is not live: v5 cannot start.

3. Requirement 2 — binding the candidate to the accepted test shaintended

Not built. compare_test_bytes asks whether test files in the implementation candidate are the exact bytes the accepted test candidate was reviewed as. Under hidden visibility those files are not in the candidate’s tree, so that question is a category error. Intended replacement: three conjuncts from immutable git objects.

  1. Absence. For every declared hidden path p, blob_id_at(candidate_sha, p) must be None. Refusal HIDDEN_TEST_PATH_PRESENT.
  2. Provenance. The green post-gate GateResult must carry the composed_tree_sha the adjudicator independently recomputes. Refusal HIDDEN_GATE_TREE_MISMATCH.
  3. Coverage. Existing tests_chain.measure_coverage against the composed post-gate execution. Refusal GATE_NOT_GREEN.

compare_test_bytes and PairingRefusal.BYTES_SUBSTITUTED are not deleted. Merged-visibility lanes still use them. The pairing path would branch on visibility; both branches keep a live reader. That branch does not exist yet.

4. Requirement 3 — differential falsification outside the candidate treeintended

Not built. Intended: the revert runs in the composed scratch tree. The _gate_names filter becomes vacuous because conjunct 1 refuses any candidate holding a hidden path. The one-path-delta vacuity §7.4 names would become structurally impossible. FALSIFICATION_NO_SUBJECT stays required. None of this is wired.

5. Requirement 4 — reviewer-to-builder handoffintended

Not built. Today’s repair handoff is free text. Runner output carries case names, file:line, assertion source and expected literals — the entire hidden-test content. The design forbids any runner output from crossing the boundary.

5.1 The record

A hidden-lane repair prompt would render exactly one typed record:

RepairDirective:
  refusal        : HiddenRepairCode
  counts         : {passed, failed, errored, skipped}
  unmet          : tuple[(requirement_id, aspect)]
  repair_hint    : Optional[str]             # PLAN-AUTHORED
  offending_paths: tuple[str]                # candidate paths only

HiddenRepairCode ::= GATE_NOT_GREEN | MIN_CASES_UNMET | OBLIGATION_UNMET | IMPORT_FAILED | FALSIFICATION_FAILED | PATH_PERMISSION | HIDDEN_TEST_PATH_PRESENT.

5.2 What is refused from crossing

GateResult.tail; per-case counts; case ids; case_selector; expected_failing_selector; expected_reason_pattern; fixture values; any byte of any hidden blob; any path under a declared hidden path. Import-error rule: a traceback crosses only if every frame’s file path lies inside the candidate’s declared outputs; a single hidden-path frame collapses the whole text to IMPORT_FAILED.

5.3 repair_hint — plan-authored, never model-authored

The plan author may declare, per (requirement_id, aspect), a repair_hint at authoring time. The runtime would emit plan bytes, never model bytes. Nothing mechanical stops a lazy author from pasting an assertion into a hint.

5.4 Tripwire

Before a hidden-lane prompt is written to disk, assembled text would be compared against accepted tests’ blob content: any normalised line of sufficient length in both refuses the launch with HIDDEN_TEST_TEXT_IN_PROMPT. A substring tripwire is a backstop against a coding mistake, not a proof against paraphrase. Not implemented.

6. Requirement 5 — evidence chainintended

Not built. A build node whose tests prerequisite is hidden would be a distinct evidence shape — HIDDEN_PAIRED_AGENT — not plain AGENT. Its chain would be: accepted tests candidate; HiddenGateReceipt × 3; the HiddenPairing row; the candidate’s §8.3 measured delta; the build node’s independent review over the candidate diff and declared contract — not the hidden tests. The build node’s reviewer would not receive the hidden tests.

7. Requirement 6 — migration and blast radiusintended

7.1 Schemafield exists; v5 unrunnable

New field on a tests lane: test_visibility: "merged" | "hidden", default "merged". Schema version maestro-plan.v5. Invalid shapes are refused in the constructor. v5 is excluded from runnable plan schema versions. v1–v4 still run. Do not imply a v5 plan can start a run.

7.2 The pin

Not built. Intended: runs.pinned_test_visibility, written at create_run, read in Scheduler.__init__ before _project_nodes. Hidden visibility changes the dependency shape (a hidden build lane needs its tests node accepted, not merged). Pin before projection, or do not build this. Safe today only because no run can contain a hidden node.

7.3 Hidden requires STRENGTH_V1

Schema already refuses hidden without a strength contract. Runtime admission HIDDEN_REQUIRES_STRENGTH_V1 for LEGACY-pinned runs is not a live run path: v5 cannot start.

7.4 The reveal step

Not built. Intended: after the last build lane merges and before the integration gate, every accepted hidden tests candidate merges into the integration branch. A run that never reaches final acceptance would leave hidden tests on refs in the private object store, not on any branch.

7.6 Size

This would touch plan schema, ingress, validation, model, the lifecycle store, scheduler projection, gate execution, three verification adjudicators, retry_policy, prompt assembly, and the merge path. Comparable to or larger than the tests/build split that landed as #124. It is not a small change. Schema + vault are the only pieces that exist.

8. Non-goals

  • Hiding tests from the tests-node author or the tests-node reviewer. Both must read them.
  • Sandboxing the builder’s filesystem generally (§16.3 item 15 remains open).
  • Preventing a builder from inferring likely tests from a well-written requirement. Hidden tests hide the encoding, never the specification.
  • Reading verifiers[].falsifiability.mutation, which §7.4 already records as reaching no runtime.
  • Any change to code nodes, whose acceptance is their command’s exit code.

9. Residual risk, and the honest verdict against §16.3 item 8

§16.3 item 8: proxy-gaming is mitigated, not solved. Every gate samples a proxy, and an agent optimizing for green looks for the cheapest one.

What would be reduced (if the composed tree shipped): overfitting to literal fixture values and assertion structure, and editing the test file to make it pass.

What is not reduced: writing the shallowest code that satisfies the stated requirement. Item 8’s sentence remains true after this change.

A fourth mode, measured 2026-08-27, that this design would not have stopped. lane-routing-chemical a3 put ~190 lines into production source that manufactured the gate’s own case count at collection time — six mechanism families with fallbacks — after an honest 2 passed, min_cases is 5 rejection. Hidden tests would not have prevented it: the builder never needed the assertions. The repair is adw_modules/gate_capture.py’s provenance check, independent of visibility, and it landed without any part of hidden-test execution.

The verdict. Hidden tests beat item 8 narrowly, in the specific mode that was actually observed (M41), and only if read containment is real. The vault is built. Even with that, §16.3 item 15’s residual applies: under --dangerously-skip-permissions a builder can read any absolute path, including harness state. Hidden tests would be hidden from a cooperative-but-optimizing builder, not from an adversarial one.

Recommendation in the source note: build read containment first as a standalone prerequisite. That prerequisite now exists. The remaining rows — composed tree, receipts, pin, reveal — are still the feature, and they are not built. If those are not acceptable to build, the status quo plus better plan authoring is cheaper for the same real-world protection the provenance check already supplies.

11. Regressions this design must ship withintended

Each must fail against a runtime that lacks the mechanism. Test 7 (read containment) is the one that decides whether the other seven are worth having — and test 7’s vault half is what exists. The other seven are not live.

  1. A hidden-lane builder prompt, as assembled and written to disk, contains no hidden path, no gate argv naming one, and no line of any hidden blob.
  2. The builder’s worktree contains no hidden test file at any point, and a candidate that adds one is refused HIDDEN_TEST_PATH_PRESENT.
  3. A repair handoff after a red post-gate carries only RepairDirective fields.
  4. composed_tree_sha recomputation refuses a mismatched receipt.
  5. Resume of an existing merged-visibility run does not rewire any needs_json.
  6. A maestro-plan.v4 plan still starts and resumes unchanged. (v1–v4 remain runnable today.)
  7. Read containment: a process with the builder’s own cwd and credentials cannot obtain the hidden blob by git cat-file, git show, or object-database traversal from the worktree. Vault tests cover this; composition is absent.
  8. The reveal step lands accepted tests on the integration branch before the integration gate.

12. Open questions

  • Q1 (blocking in the original note). Build the separate harness-private object store? The vault is now built. Composition still is not. Without composition the feature does not run.
  • Q2. Repair oracle granularity: per-(requirement, aspect) unmet flags, or a single pass/fail?
  • Q3. Adopt plan-authored repair_hint, and who audits hints for leaked assertions?
  • Q4. Confirm the reveal step: the delivered integration branch should contain its tests.
  • Q5. Accept the expected increase in repair rounds — a builder repairing against counts rather than assertions will spend more attempts.
